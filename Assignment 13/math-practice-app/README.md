# Math Practice App

A React + TypeScript app (built with Vite) for children ages 7–12 to practice addition, subtraction, multiplication, and division with flip-card multiple-choice questions. See `Assignment 13/Project Docs` for the full specification and implementation plan.

## Scripts

| `npm run dev`           | Start the development server                                       |
| `npm run build`         | Type-check and build for release                                   |

## Testing

Tests sit next to the code they check (`Thing.tsx` / `Thing.test.tsx`; extra files such as `PracticePage.leave.test.tsx` cover one topic). Page and app tests render the real routes with `AppRoutes` inside `TestRouter` (`src/test/`), a data router like the one the app uses, and click through them with Testing Library, so they exercise the same code as a student. `npm run test:coverage` prints the numbers and writes an HTML report to `coverage/` (git-ignored); it is about 99% of statements and branches. What is left is code that cannot be reached, such as a server-rendering fallback and a float-rounding guard.

**Accessibility testing (task 82)**

- _Automated:_ `src/app/accessibility.axe.test.tsx` runs axe-core over every page and state (dialogs, the practice card both sides, the summary, the open menu, notices and the error message) against WCAG 2.0–2.2 A/AA and axe's best-practice rules. jsdom has no layout, so colour contrast and target size are switched off there; `designContrast.test.ts` and `touchTargets.test.ts` cover them by reading `index.css`.
- _Keyboard only:_ `AppRoutes.keyboard.test.tsx` runs a whole visit (setup, five questions, summary, home) with Tab, Space, Enter and arrow keys only. Writing it found a real problem, now fixed: after a verdict the card was replaced and focus fell back to the top of the page, so every question cost a trip through the header. The new question card now takes focus (`focusOnShow`).
- _In a real browser:_ axe was run on every page and state at desktop size and at 320px (which is what 400% zoom looks like), including WCAG 2.2 target size and best-practice rules, with no violations. To repeat it, open the dev server, paste the contents of `node_modules/axe-core/axe.min.js` into the console (or `fetch('/node_modules/axe-core/axe.min.js')` and `eval` it), then run `await axe.run()`. The "needs review" items axe reports for colour contrast are the decorative `✓` and `−` marks, which are `aria-hidden` and cannot be measured.
- _Zoom:_ checked at 320px wide (400% zoom), and at 320px with text enlarged 200% (large system font on a small phone). That last case did overflow on the practice card and heading, because sizes written in rem grew with the text but not the screen; they are now capped by the screen width (`designContrast.test.ts` guards this).
- _Reduced motion:_ `usePrefersReducedMotion.test.tsx` and `PracticePage.a11y.test.tsx`.
- **Not done: a real screen reader.** NVDA, JAWS, VoiceOver or TalkBack were not available. What is checked instead is the markup a screen reader works from: roles, names, landmarks, the live announcement that reads questions in words, and the accessibility tree. Someone should still try a session with a screen reader before release.

## Notes for later phases

- **Settings (Phase 11, done):** the Settings page saves automatically through `useSettings().updateSettings`; the session summary's **Change Settings** panel now links to both _Practice Setup_ and _App Settings_. `usePracticeDefaults` reads the saved defaults for the setup page. Card animation and explanations take effect during practice. **Sound effects** is saved but has no effect until sounds are added (no phase covers audio; the spec lists it under future work).
- **Mistake patterns (Phase 12, done):** every answer the student marks wrong goes through `recordPracticeAttempt` (`services/attemptRecorder.ts`), which saves it, counts it in the statistics and updates the patterns (`recordAnswer`). A pattern's id is `operation:first:second:L<level>` (e.g. `multiplication:8:7:L2`), so the same mistake can never be stored twice; 7 × 8, 8 × 7 and the same fact at another level are different patterns. A repeat miss adds one to `incorrectCount`, updates `lastIncorrectAt`, and **resets** `similarCorrectCount` to 0 and `mastered` to false. Capped at 1,000 (mastered, then least recent, dropped first). `useStatistics` loads them for the Statistics page.
- **Accessibility (Phase 16, done):** keys 1–4 choose an answer (`useAnswerShortcuts`; ignored in text fields and with Ctrl/Alt/Meta, and off while the End Session dialog is open); answers show their key and carry `aria-keyshortcuts`. Screen readers get polite live announcements: the question and progress on every new question, the chosen answer, and the revealed answer in words (`utils/speech.ts`, never the symbols). After a page change the tab title updates and focus moves to the new heading (`AppLayout`). `usePrefersReducedMotion` plus the card-animation setting decide whether the card flips or just swaps. Colours are checked against WCAG AA by `designContrast.test.ts`, which reads `index.css` — interactive edges use `--color-border-strong` and the focus ring uses `--color-focus`, so don't use the faint `--color-border` for controls. Layout was checked at 320px wide and at 200% text with no sideways scrolling; keep new grids using `minmax(min(Xrem, 100%), 1fr)`. The automated axe check and keyboard-only run were added in Phase 20 (see Testing above); a real screen reader has still not been tried.
- **Responsive design and polish (Phase 17, done):** below 600px the header shows a **Menu** button (`aria-expanded`, `aria-controls`) and the links fold away; wider screens always show them. The menu closes on Escape (focus returns to the button), when a link is chosen, and on any page change (`Header` keeps the path it was opened on, so there is no reset effect). The practice page is centred in `.practice-session` (max 46rem); from 700px up the question and answer tiles are bigger, and `(pointer: coarse)` adds extra room for fingers. `touchTargets.test.ts` reads `index.css` and fails if a control drops under 44px or the menu rules change; phone and tablet sizes (320–414px, 768×1024, 1024×768) were checked in a browser for sideways scrolling and small targets. Encouraging messages are a setting (`feedbackEnabled`, on by default): `utils/feedback.ts` picks a message after each answer (never the same twice in a row, never blame) and a closing message on the summary. The on-screen note is `aria-hidden`; screen readers hear it at the start of the existing live announcement. In CSS, a media-query override must come **after** the base rule it changes (same specificity, last wins).
- **Similar questions (Phase 13, done):** `generateSimilarQuestion(pattern)` makes a question from a mistake using nearby numbers, reversed operands (addition and multiplication only) or the fact family, always at the pattern's own level, and labels it `mistake-review` with the pattern's id.
- **Mistake review (Phase 14, done):** the setup page's "Practice my mistakes" option (and the summary's "Practice Mistakes") is available while at least one pattern is not mastered (`useActiveMistakeCount`). A review session (`services/reviewSession.ts`, `utils/mistakeReview.ts`) picks patterns at random weighted by priority (more misses, more recent, less review progress), never the same pattern twice in a row, and avoids repeating recent problems. Each answer is saved with its `mistakePatternId`. A **right** review answer adds one to `similarCorrectCount`; the pattern is **mastered** at `masteryThreshold` (Settings, default 3; the count is also checked against the current setting, so lowering it applies straight away). A **wrong** review answer counts as another miss on the same pattern (progress resets, no new pattern is created for the similar question). Mastered patterns are left out of review and come back after a later mistake. A review session ends early when every mistake is mastered. Its summary shows the operations and the most common level of the mistakes it used.
- **Mistake statistics (Phase 15, done):** the Statistics page shows how many mistakes need practice or are mastered, the review practice totals, the operation(s) missed most (ties show every tied operation), the five number facts missed most (ties broken by most recent), and every mistake with its review progress. Mastered mistakes sit in a collapsed section of their own. The review totals are part of the running statistics (`statistics.review`), so trimming old attempts does not change them; saved totals without that part are rebuilt from the saved answers. `useStatistics` loads the patterns too, so Reset Statistics clears everything shown.
- **Saved data (Phase 9):** the browser keeps `mathPractice.version`, `.settings`, `.sessions` and `.attempts`. The `.statistics` and `.mistakePatterns` keys are used from Phases 10 and 12, and `.activeSession` (Phase 18) holds the session in progress. `AppProvider` loads and saves settings, and `clearAllData()` (Settings page) erases every `mathPractice.*` key and restores the defaults.
- **Release preparation (Phase 22, done except the deployment itself):** see [`RELEASE.md`](RELEASE.md). The app has a plain-language **Privacy page** (`/privacy`, footer link) and `src/utils/privacy.test.ts` keeps its promises true by failing on any network call, cookie, analytics or advertising code, outside link, extra library, or weakened hosting header. The security headers (a strict Content-Security-Policy that allows only the site itself, no referrer, no type guessing) are written once in `public/_headers`, repeated in `vercel.json` (a test checks they match) and sent by `npm run preview`, so the production build can be tried under the real policy. `public/_redirects` and `vercel.json` make every address show the app (a refresh or shared link works). The build's base path is `VITE_BASE` (default `/`) and is also the router's `basename` and the error page's home link. `.github/workflows/math-practice-ci.yml` runs `npm run verify` on every change (it deploys nothing). The production build was checked in Chromium only (all routes, a full session, reload persistence, phone and tablet sizes, CSP enforcement); **Safari, Firefox, Edge, real phones/tablets and a screen reader were not available** and are listed as manual checks. **Nothing has been deployed**: that needs the owner's hosting account.
- **Performance and data management (Phase 21, done):** measured first, then fixed. Numbers are from a desktop browser with a full-size history (200 sessions, 1,000 mistakes, thousands of answers); phones are typically 4–6× slower, and a slow-device test was **not** possible here (no CPU throttling), so those multiples are estimates.

  | What                                                   | Before       | After        |
  | ------------------------------------------------------ | ------------ | ------------ |
  | Saving one answer (5,000 attempts kept)                | 44 ms        | 3 ms         |
  | Redraws of the practice page per tap                   | 2            | 1            |
  | Opening Statistics with 1,000 mistakes (development)   | 717 ms       | 118 ms       |
  | …the same in the production build                      | not measured | 45 ms        |
  | Reset dialog open/close on Statistics (1,000 mistakes) | 400 ms       | 20 ms        |
  | DOM nodes on Statistics (1,000 mistakes)               | 6,966        | 672          |
  | Saved data for that history                            | 2.05M chars  | 0.40M chars  |
  | Main JavaScript (gzip)                                 | 388 kB (120) | 376 kB (118) |
  | Favicon                                                | 9,522 bytes  | 204 bytes    |
  - **Saving an answer:** it used to read and check the whole saved list three times and rewrite it. `addAttempts` (`practiceHistory.ts`) now reads it once and says what it had to drop, and `recordAttemptOnce` returns whether the answer was new. A test counts the reads. Production build with the full history: choosing an answer 2.8 ms, flipping 2.5 ms, a verdict (save, totals, mistakes, next question) 15 ms.
  - **Data size:** nothing displays individual attempts; they are only used to skip repeats and to rebuild damaged totals. So `MAX_STORED_ATTEMPTS` is now 1,000, and answers pushed out are first added to `mathPractice.attemptArchive` (`addStatistics`, `rebuildStatistics`), so a rebuild is still exact (it used to undercount once old answers were trimmed). Reset Statistics clears the archive too; a damaged archive is dropped quietly by the startup repair. An old 5,000-record list is trimmed (and archived) the first time an answer is saved. Sessions stay capped at 200 and the Statistics page lists the latest 10. If the browser is full, `saveList` still drops the oldest 25% and retries; those are not archived (a rare case).
  - **Storage use:** `measureStorageUsage()` counts characters per saved item; Settings shows "Saved on this device: about N KB". Browsers allow roughly 5 million characters per site, so a full-size history now uses about 13% (it was about 41%).
  - **Rendering:** the practice card keeps its progress in a ref (not state) and writes the refresh bookmark directly, which removed the second redraw per tap. `PracticePage.renders.test.tsx` guards one redraw per action. The mistake lists show 25 at a time with "Show 25 more" (focus moves to the count when the button goes away), `MistakeDetails`, `MistakeStatistics` and `FrequentlyMissed` are `memo`ised, and their splits and sorts are `useMemo`ised. Question generation was already outside render (state initialisers and handlers).
  - **Loading:** Statistics and Settings are code-split (`app/lazyPages.ts`, `React.lazy` plus a `Suspense` fallback in `AppLayout`) and fetched in the background when the browser is idle, so opening them is instant. Moving between pages keeps the old page on screen until the new one is ready (no flash); a direct visit shows "Loading…"; a failed download shows the friendly error. The saving is modest because the framework is most of the weight (about 193 kB react-dom and 113 kB react-router of ~380 kB, against ~65 kB of app code); there were no unused dependencies, fonts or images to remove (only the favicon, which was still the default Vite logo and is now a small hand-written icon).
  - **Re-measure** with a seeded browser (the dev server serves modules, so `await import('/src/services/…')` works in the console), `npm run build`, `npm run preview`, and the Performance API.

- **Error handling (Phase 19, done):**
  - **Damaged saved data (task 76):** `main.tsx` runs `ensureSchema()` then `repairStoredData(schemaStatus)` (`services/dataRepair.ts`) before anything renders. It handles one kind at a time (settings, sessions, attempts, mistake patterns): a kind that cannot be read at all (bad JSON, wrong shape) is **reset**; a list with some unusable records keeps the good ones (**repaired**); settings keep every valid field and only damaged ones go back to the default (a setting that is just _missing_, from an older version, is not damage). Totals are rebuilt from the saved answers and an unusable session bookmark is removed, both quietly. It does nothing when the schema status is `newer`, `failed` or `unavailable`, so data from a newer version is never destroyed. What it changed is passed to `AppProvider` (`dataProblems`) and shown by `DataRepairNotice` ("We fixed some saved data…", dismissible).
  - **Saving fails (task 78):** `writeItem` reports every failed save to `services/storageFailures.ts` (`quiet: true` lets a caller that will retry report it itself; `saveList` does this so a successful trim-and-retry is not reported). `StorageWarning` shows a plain-language message per reason (`utils/storageMessages.ts`), once per kind of failure, and stays closed once dismissed. `test/setup.ts` resets that store after each test.
  - **Question generation (task 77):** `generateQuestion` retries the whole question up to 5 times (the draft inside also retries 5 times) and then throws `QuestionGenerationError`. The app uses the `…Safely` versions (`generateQuestionSafely`, `generateNextQuestion`, `generateSimilarQuestionSafely`, used by `nextReviewQuestion`): on failure they log through `utils/devLog.ts` (development builds only) and use a hand-written fallback (`services/fallbackQuestions.ts`; one problem per operation and level, checked by tests against the real rules; a review question asks the mistake itself again, still credited to its pattern). The strict versions still throw, so tests can see failures.
  - **Error screens (task 78):** `ErrorBoundary` wraps the page area in `AppLayout` (reset on every page change, so the menu keeps working); `RouteError` is the router's `errorElement` for anything outside it. Both show `ErrorMessage` (plain words, no stack trace, a plain `<a href="/">Go Home</a>` that reloads the app) and log details in development only. A page with nothing to show (practice with no session, summary with no results, review with no mistakes) redirects to setup with a `notice` in the navigation state (`utils/setupNotice.ts`), which setup explains.
  - Not covered: errors thrown inside event handlers or async code are not caught by an error boundary (React only catches render errors).
- **Statistics (Phase 10):** `recordAttempt` (in `statisticsService.ts`) saves an answer and adds it to running totals kept under `mathPractice.statistics`, exactly once. Sessions are capped at 200 and detailed attempts at 1,000 (oldest dropped first; it was 5,000 until Phase 21), but the totals are never recounted from them, so trimming does not change the statistics. Dropped attempts are folded into archived totals first (see Phase 21), so even rebuilt totals stay complete.
- **Resetting (Phases 10 and 12):** "Reset Statistics" calls `resetPracticeHistory`, which erases sessions, attempts, statistics and `mathPractice.mistakePatterns`, and leaves settings alone. Mistake patterns are stored under that key, so a reset clears them.
- **Session recovery and leaving safely (Phase 18, done):**
  - **Recovery:** while a session runs, `usePracticeSession` keeps a bookmark under `mathPractice.activeSession` (`services/activeSessionService.ts`): the session, its answers, the question showing, a review session's notes, and the card's progress (answer picked, card turned). It is tied to the router's `location.key`, so a refresh of the same page visit resumes it ("Welcome back!"), while "Practice Again" or any fresh start (new key) never does. Everything is re-checked on load (`parseActiveSession`); a damaged or inconsistent bookmark is ignored and a new session starts. It is removed when the session ends and by Reset Statistics / Clear All Data. Resumed answers are filed again by id (`recordPracticeAttempt` skips ones already saved), so nothing is counted twice or lost. Mistakes are not stored in the bookmark; they are reloaded, since they are saved answer by answer. Not done: offering to resume from the Home page after the tab was closed (the bookmark only matches the same history entry).
  - **Leaving:** the app now uses a data router (`createBrowserRouter` + `RouterProvider` in `App.tsx`), because `useBlocker` needs one. While a session is running, any trip away (a header link or the browser's Back button) opens "Leave this session?"; **Keep Practicing** (or Escape) stays, **End Session and Leave** ends and saves the session and continues to where they were going (not the summary). Nothing is asked once the session has ended, including on the summary page. `useBlocker(!isComplete)` is called above the effect that navigates to the summary, so a session that finishes by itself is not blocked by its own guard. Closing or refreshing the tab is **not** intercepted with a browser `beforeunload` prompt, since recovery makes it safe.
  - **Tests:** pages that use `useBlocker` need `TestRouter` (`src/test/`) instead of `MemoryRouter`.
